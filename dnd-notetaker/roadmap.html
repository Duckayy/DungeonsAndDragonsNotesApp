DD NoteTaker — Full Stack Roadmap

Tech stack, permissions model, and the build sequence for the Supabase migration + remaining features.

Permissions Model

DM (Campaign Owner)

Full read/write on every campaign they own. Can invite players, mark specific pages visible to players, and revoke a player's access at any time.

Player (Invited Member)

  • DM's notes — view-only, and only for pages the DM has explicitly marked visible. Hidden is the default, so story-critical notes stay invisible unless deliberately shared (e.g. a map or a character portrait).
  • Their own personal notes — full read/write. Isolated from the DM's notes and from other players' notes.
  • If revoked — full, immediate cutoff. No read or write access at all, campaign disappears from their list entirely.
Enforcement happens twice: a client-side check hides buttons/pages for UX, and a Postgres RLS policy is the real boundary — so a bug in the UI can never leak DM notes or grant write access it shouldn't.

Build Sequence

  • 0a — Supabase Setup & Auth no dependencies

    Supabase project; users/campaigns/campaign_members schema; login/signup UI; MFA.

  • 0b — Storage Layer Migration depends on 0a

    storage.js rewritten to call Supabase internally, same public function signatures for existing callers.

  • 0c — Revision History depends on 0b

    View/restore earlier versions of a note — restoring creates a new revision on top, nothing is ever silently lost.

  • 0d — Personal Notes + Visibility Toggle UI depends on 0b

    Player-owned notes; the DM-facing "visible to players" toggle per page; invite/revoke UI.

  • 0e — One-Time Data Migration depends on 0b

    Move existing localStorage campaigns/sessions into Supabase, once, under the DM's account.

  • 3 — Character Tracker depends on 0b, 0d

    Confirm the Character data model; build characters.js directly against Supabase.

  • 4 — World-Building depends on 0b, 0d

    Confirm the Location data model; build world.js; Leaflet.js maps.

  • 5 — Polish depends on 3, 4

    Markdown editing, tag organization, cross-cutting polish once everything above exists.

0c and 0e can happen in either order — both only depend on 0b. 0d lands before Units 3/4 so Characters and World-Building get the visibility pattern from day one instead of retrofitting it later.

Implementation Note (learned partway into building Unit 0a)

storage.js's functions (saveItem/loadItem/deleteItem/listItems) must become async once any part of them talks to Supabase over the network. That means every current caller — campaigns.js, sessions.js, sessionPanel.js, and nav.js's migrateSessionsToDefaultCampaign — needs to be updated to use await, not just the campaign-specific code paths. Decided: fix all callers in Unit 0a itself, rather than leaving sessions/characters silently broken until Unit 0b.
